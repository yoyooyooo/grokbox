# Manual compaction through the unified management owner

2026-09-21. CTX-04 / CONT-07 / CLI-05 implementation stage. This records bounded implementation evidence, not deployment or complete native/App acceptance.

## Current entry and owners

`bot context compact <bot> --preview` reads the exact owned Box scope, loaded native default-session capability, selected model and cost-policy revision. It loads no context body, initializes no CONT database, and requests no summary. A confirmed submission requires the original request UUID, account scope and reviewed revision. The revision binds the account, loaded Host generation, selection and cost policy; **it is not a snapshot or CAS of the future native root**. Native admission uses the then-current idle default Box root. Named/server/subagent sessions are not silently mapped to that root.

The shared client and Server reuse the original native manual facade, Unix modeld, context maintenance kernel, Pi-derived algorithm and Host checkpoint owner. Only the management declaration and dispatch/settlement records are added to the existing CONT `continuity_queued_controls` table. No second algorithm, generic operation database or CLI-executed business writer is introduced. `context.compact` is separate from context read/write/activation permissions; native ownership and captured policy remain independent checks. The native/schema/modeld boundary rejects manual requests without an exact approval; ordinary preflight/overflow cannot carry manual authority.

`operation get`, `reconcile`, `resume` and `cancel --domain compaction` consume the original request. Reading and replaying a completed request do not execute it again. Only an undispatched preparation can resume its immutable plan or be cancelled. Unknown dispatch is observed, never retried under a new UUID. The CONT transaction refuses conflicting unresolved current-state changes or compaction on the same Bot and does not evict unknown records to admit more work.

## Native completion and uncertainty

A modeld checkpoint receipt is not proof that the enclosing native shell has finished. The original Host job publishes its own returned/failed/unknown settlement; reconciliation requires that exact job and loaded generation. A normal summary failure is retained as a settled failure and permits a new explicitly approved request; uncertain checkpoint or cleanup stays unknown and blocks replacement requests. An unchanged/no-op result consumes its request as well and cannot acquire new work after later user input.

The management Server owns an accepted HTTP operation independently of the client connection. Server shutdown cancels its native HTTP connection and joins its own pending CONT writes; it does **not** claim to stop the independently owned Host job. A packed Server killed after native checkpoint but before shell cleanup restarts with the original unknown record. Only the original native settlement can resolve it, and dispatch/checkpoint remain single. A new user input waits behind maintenance; no synthetic user message or ordinary task is created.

## Consumers and retired implementation

The former `agents context` / `agents compact` registration, CLI dispatch, direct Gateway method and unused mock handler have been removed, not redirected. Native RPC access remains solely in the Server's bounded adapter. Explicit approval is rechecked by Host/modeld; the Server rechecks capability after durable claim and before dispatch. A claim acknowledgment loss or interruption at that boundary cannot authorize a second call.

The client snapshots input before awaiting credentials, checks complete receipt identities and refuses mismatched settled failures as unknown. Reproduced counterexamples covered getter/coercion inputs and a failure receipt bound to another Bot. Browser plan hashing uses native WebCrypto over the **same canonical declaration** as Node: real Chrome found that a synchronous Node hash worked during SSR but broke later browser refresh. No crypto shim or second revision grammar was added.
