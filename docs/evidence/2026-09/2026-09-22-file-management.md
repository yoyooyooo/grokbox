# Named-root files through the shared management owner

CLI-05 W3 / DATA-01 / CLI-03 / CLI-04. Continues the existing management worktree after the [Job cutover](2026-09-22-job-management.md). This is the named-root filesystem vertical path, not W4 acceptance or proof of native Memory/Project attachment support.

## Scope and original owners

The existing management Server now owns the original Box `GovernedFilesystem`, not another filesystem executor. The current `file` commands and Web `/files` share the browser-safe client and pure file contract. Exact references bind installation, root policy, physical root inode and relative path. Metadata, content, write, delete and restore permissions are independent. Configured roots cannot overlap the management installation, each other or material/native sources; an unavailable or replaced source never selects a different root. Job execution retains its separate service-owned process authority and does not regain a daemon file API.

The original material SQLite owner now declares schema 2. Its existing text-operation table and new file-operation table retain separate domain receipts, while one transaction checks unknown physical paths and ancestor/descendant conflicts across both domains. There is no new database, general task engine, cache writer or cross-store transaction. A named-root operation cannot be bypassed by changing the same path into an indexed writable source. The original indexer still owns derived scans; source publication and index adoption remain different facts. Old schema bytes and lost safety ledgers are not upgraded, replaced or reinterpreted as fresh authorization.

Each change records the principal-scoped original request and canonical input digest before the original adapter may publish. Duplicate requests inspect the original receipt before current source admission. An uncertain claim or publication protects the path; new UUIDs or service generations do not replay it. Metadata and receipts contain no body or credential. The physical-path fence protects participating writers, not arbitrary external processes that rename the tree or deliberately delete every safety footprint.

## File publication and binary lifetime

Direct content reads are bounded base64 with actual hash verification. Larger files use a fixed original descriptor, 32 KiB chunks and a complete size/SHA-256 check, up to 64 MiB. Simultaneous opens count toward the same finite descriptor budget; identical open requests share one in-flight acquisition. Partial, changed or incorrect bytes never become a verified download. CLI downloads publish a new caller-local file only after hashing and sync, using no-clobber linking. Browser downloads release a verified binary to the browser; that is not a guarantee that the user saved it durably.

New destination files use no-clobber linking; replacements retain the original parent descriptor, expected revision and independent readback. Readback must match the original intended bytes, not a concurrent writer's newer content. Existing-file replacement and directory restore do not claim external compare-and-swap. A directory revision describes its own entry metadata, not a recursive content snapshot. Symlink/hard-link checks, blocked private paths, bounded traversal and original target serialization remain in the original adapter.

Upload staging is not publication. The original idle timer retires its own uncommitted descriptor and reports that fact to the durable domain owner; capacity and pending-path permission are released only after the original cancellation is recorded. This is not another scheduler or a GET that invents a cancellation. A submitted commit, uncertain publication or dead service owner cannot be cancelled as though nothing happened. A successful upload cannot be labelled cancelled. Shared-client success and refusal receipts both bind the original source and request; a settled refusal returns nonzero status, not an apparently successful CLI command.

Delete moves the exact reviewed object into owner-private root-local trash. Restore references the same principal's original successful deletion and the original destination, not an arbitrary trash path or another principal's receipt. An existing competing destination is preserved. Disposal is not irreversible deletion or permission for diagnostic garbage collection to remove user files.

The management lifetime owns admitted work after caller disconnection. Shutdown aborts pending authority and awaits the actual file and SQLite settlement before releasing its gate. Hard-exit tests kill only a disposable packed management Server, after the original claim or after actual publication. Restart reads the original unknown and does not publish again. The fixture owns and removes its private test files; no live Host, business Job, real Bot, provider or external notification is invoked.

## Consumer cutover

`file root list/get`, named-root `file stat/list/read/write/mkdir/upload/download/delete/restore`, `operation get --domain file`, and explicit original staging cancellation replace the eight `fs` leaves. The 14 daemon file RPCs, daemon resource acquisition/cleanup, handshake filesystem projection, Profile file-capability promises and old CLI file writer are removed. There is no alias or refusal-only implementation under the old names. Negative tests confirm the remaining daemon cannot service the retired methods.

Existing material references still use their original source-specific text writer and permissions, not an index update or a fallback to the new named-root path. `file list` without a named-root reference searches the existing indexed window; an explicit directory reference performs direct metadata listing. Skills, command mapping and LIVE coverage distinguish these two source types. Native User/Project writes, Project attachment fileRefs, upstream account/synchronization qualification, cross-domain events and safe long-term storage/trash retirement remain DATA-01 and related source-ticket obligations.

The browser explicitly reviews the source revision, preserves drafts on conflicts, selects a local upload file, confirms publication and recovers original requests. It renders text as data, not markup. Content reads and downloads are explicit. Its local storage contains only installation/principal/source/request locators, not binary content, reusable approvals, model credentials or deletion payloads. After a missing response, reloading and querying history does not send the change again. Unknown upload recovery can ask the current owner to cancel its original staging area, but cannot authorize replay. Restore is a separate explicit action against the original deletion.
